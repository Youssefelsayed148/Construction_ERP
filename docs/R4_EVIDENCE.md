## R4.1 password hash choice and after measurement

The password service uses the OWASP Password Storage Cheat Sheet's listed scrypt set `N=2^15, r=8, p=3` (32 MiB working memory), with Node `maxmem=64 MiB`, a random 16-byte per-password salt, a 64-byte key, and timing-safe comparison. See [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). The selected set took 140.7 ms for a single hash in the initial local benchmark. On production Node `v20.20.2`, 50 concurrent derivations completed in 1,009.3 ms with `UV_THREADPOOL_SIZE=16` (50 concurrent hash calls consume up to 512 MiB at 16 active workers). A 16-worker pool was selected to match the 16 logical CPUs; the same Node 20 measurement was slower at 32 workers (1,036.3 ms) and default four workers took 2,271.5 ms. Larger OWASP-listed sets did not improve latency at concurrency 50 on this host; the chosen set is the best-performing 32 MiB option measured.

The production Docker image now sets `UV_THREADPOOL_SIZE=16`; the R4 PG runner also sets it before starting Jest. No dependency was added. The app's 10-request invalid-login burst on the same Windows host measured 42.12 requests/s after the change vs. 4.58 requests/s before. The baseline event-loop reporter's p95 sample was 809.50 ms; after scrypt, the maximum sampled 100 ms-window p95 was 23.74 ms. Reporter windows changed from one second to 100 ms so the shorter burst was sampled. Both runs returned the expected 10/10 generic 401 responses.

At c=50 in the isolated production Node 20 crypto benchmark, this OWASP-listed set's hash-completion p95 was 913.2 ms; the review's aspirational login p95 target of 500 ms is **not met by this isolated high-concurrency hash benchmark** on this host. The full app was not measured at c=50 after the change. The lower-memory OWASP option (N=2^13,r=8,p=10) still measured 700.3 ms p95 at c=50 with 32 workers, so it did not meet that target either. Do not claim the c=50 target passed.

## R4.2 shared limiter and sweep proof - 2026-10-15

The process-local auth, unauthenticated v1, and MCP rate-limit Maps were replaced by atomic Postgres fixed-window counters. Raw IP/user subjects are hashed with SHA-256 before storage. A cleanup query deletes counters older than one day every 1,000 requests per process; cleanup errors are logged and do not break an otherwise successful request. Counter query failures fail closed with a typed 503 and Retry-After. Over-limit results return 429. The separate authenticated v1 limiter already used the migration-0040 Postgres counter and remains unchanged.

Sweep leaders retain the session advisory lock, delete ledger entries older than 30 days, and enforce a minimum interval after obtaining the lock. Production interval wrappers set this minimum to their configured interval; direct invocations retain a zero minimum unless supplied. Concurrent lock losers and minimum-interval suppressions are recorded as skipped runs.

## R4.3 graceful shutdown, timeouts, cancellation, and pool metrics - 2026-10-15

The server now handles SIGTERM and SIGINT by stopping new accepts, clearing leader-locked sweep timers and the outbox timer, draining HTTP requests, and closing the PostgreSQL pool. HTTP drain is bounded at 25 seconds by default; remaining sockets are force-closed and pool shutdown has a five-second bound. HTTP headers (15 s), requests (120 s), keep-alive (5 s), and socket timeout (120 s) are configured and validated. Timeout values can be changed with the `HTTP_*_TIMEOUT_MS` variables.

New PostgreSQL sessions set `statement_timeout=30s`, `idle_in_transaction_session_timeout=1min`, and `lock_timeout=5s` by default; `DB_STATEMENT_TIMEOUT_MS`, `DB_IDLE_TX_TIMEOUT_MS`, and `DB_LOCK_TIMEOUT_MS` are validated process-environment overrides. SQL statement, lock, and idle-transaction cancellations are typed 504 errors; connection exhaustion/outage and a disconnected cancellable read are typed 503 errors with Retry-After. English and Arabic error keys are paired. The report data, export, and project report read paths use a dedicated checked-out client and destroy that connection if the client disconnects, cancelling the running SQL without leaving a transaction open. `/api/v1/ops/metrics` now includes only pool total, idle, waiting, and max counts.
