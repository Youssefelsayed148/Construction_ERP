## Route and navigation baseline

- `frontend/src/App.js` has a single authentication-only `ProtectedRoute`; it does not provide a reusable module/action permission route guard. Project navigation already has project-scoped filtering through `utils/projectNav.js`.
- `frontend/src/components/layout/Sidebar.js` filters menu items against `policy_modules` and `policy_permissions`. New top-level items need matching namespaced `navigation.items.*` keys and module/action declarations. Project screens should be nested in the existing project shell and inherit its project context.
- Current relevant route coverage: `/inventory`, `/hr`, `/approvals`, `/settings`, `/agent-activity`, and project pages including `/projects/:id/documents` and `/projects/:id/handover`. No route exists for the other requested management screens.

## API client and forms baseline

- Direct API use: 61 `fetch(` call sites across 41 files in `frontend/src`; 0 axios references. Calls are spread across `services/api.js`, page-local `fetchApi` helpers, and components, with inconsistent token headers and error parsing. This count is the R5.1 starting baseline; add a guard that ratchets down direct calls.
- Existing centralized service module: `frontend/src/services/api.js` contains auth, user, dashboard, and account-mapping service helpers. It does not yet centralize every request, cancellation, typed API errors, or pagination headers.
- Existing form kit: `components/common/FormField.js` provides labels and accessible error/hint wiring; `components/common/formUtils.js` provides `validateValues` and `mapServerErrors`; shared `States` components provide loading/empty/error patterns. `TextEntryDialog` is an existing small form dialog. There is no external form library and no reason to add one.
- New screens should use the existing kit, disable submission while saving, show server errors, accept an abort signal for reads, use logical CSS properties, and keep EN/AR namespace keys paired. Existing `PermissionButton` can gate individual actions; a route-level permission guard still needs to be added.

## Current implementation status - 2026-10-15

- R5.1 now routes all frontend `fetch` use through `services/apiClient.js`; the direct-call guard is at 1 call (the client implementation) versus the original 61 across 41 files. Typed errors, 401 handling, abort-on-route/unmount, and `X-Total-Count` support are implemented.
- R5.2 adds `useManagedForm`, `FormActions`, and `LoadMore` using the existing field and validation helpers. No new dependencies were added.
- R5.4 uses a bilingual `/admin/:area` workspace with role/module route checks and filtered sub-navigation. Routes cover organizations, users/roles, delegations, approval limits, inventory documents, variations, claim SLA, webhooks, API tokens, document numbering, and replenishment. The project-specific views take a project ID; inventory routes pass project/warehouse scope to existing APIs. Lists expose a load-more control using `X-Total-Count`.
- Backend contract limits: there is no user-create endpoint or role-definition CRUD, so users can only be listed, edited, deactivated, and assigned an existing role. Delegations have create/deactivate but no edit. Approval limits have list/upsert only. The claim SLA API is read-only; the screen lists claims and views SLA detail. Numbering is a project-scoped read/update. Replenishment policies use the existing upsert and override deletion operations. No endpoint was added for these gaps.
- Secrets from webhook creation/rotation and API-token creation are held in component state and displayed until dismissed; list data does not include secrets and no code logs them.
- R5.3 is implemented: the API-backed list screens in the pagination-impact inventory now use shared `LoadMore` controls with `limit`, `offset`, append behavior, and `X-Total-Count`. Project Wizard and Project Detail employee/client/manager lookups are included. The Dashboard remains a summary of bounded alert previews with links into the full module registers; Login and Settings have no list views. Project phases/team/milestones are supplied together by the project-detail response rather than as paginated list endpoints.
- The project does not include React Testing Library and R5 rules prohibit adding dependencies; new screen tests use the existing React DOM test harness. No visual, RTL-appearance, or real-browser check has run.
