SECTION 01

Get it running & sign in

Two ways to bring the stack up. Both end with a browser on the frontend and an Express API on :5000.

Option A — Docker (one command)

From the repo root, with a .env holding DB_PASSWORD and JWT_SECRET:

  • docker compose up --build — starts Postgres, the backend, and the frontend (served on :8090).
  • To preload seeded/test data, drop the handed-off SQL dump at db_dump/init.sql before the first boot — Postgres auto-runs it only while its data directory is empty.

Option B — Local dev

  1. node backend/src/scripts/setupDb.js — creates the database, all base tables, the chart of accounts, and the seed owner login.
  2. node backend/src/scripts/migrate-*.js — run each migration script in order. They are standalone and idempotent; the local DB drifts from route code regularly, so run them all.
  3. node backend/src/scripts/seed-test-data.js — 3 clients, 3 suppliers, 6 inventory items, supplier↔material links, and two projects (PRJ-SEED-1 fully populated, PRJ-SEED-2 BOQ only). Safe to re-run — every row is keyed on a fixed SEED- marker.
  4. node backend/server.js and npm start in frontend/.
  5. Optional: node backend/create_test_users.js adds test-finance-mgr@test.com and test-staff@test.com (both test123) so you can exercise multi-role approval flows.

Who you can log in as

Auth is email + password → a 7-day JWT. The token carries only a user id; every request re-loads the user. Roles seen in the code:

RoleWhat it can do
owner / adminEverything. The authorize() middleware short-circuits to allow for these two, and they see every pending approval regardless of stage.
finance_managerStage-1 approver for expenses and payroll.
legal_mgrStage-1 approver for legal documents.
maintenance_mgrStage-1 approver for assets and maintenance.
project_managerStage-1 approver for project_budgets and sub_contracts. (This is a login role — distinct from a project's staffing "Project Manager", see §4.)
purchasing_mgrListed among privileged approval roles; purchase-order tables aren't present in this DB build.
staffDefault. Can create records and raise approval requests; can't approve.

New logins are minted by an owner/admin via User management (POST /api/auth/register).

Navigation map

Everything project-specific lives one level down: Projects → a project card → Project Detail, which links out to six sub-module tabs (/projects/:id/boq, /work-orders, /site, /qhse, /documents, /units).

SECTION 02

The company cycle at a glance

Before touching a screen, hold this shape in your head. A client signs a contract; that becomes a project with a priced BOQ (the budget). Work is dispatched as work orders against BOQ sections. As crews report progress, verified work completions push quantities back into the BOQ and fire cost events that accrue into project costs. Money flows the other way: invoices are raised against the project, payments land against invoices, and the finance view nets it into profit. Real-estate projects add a units & sales branch that auto-invoices on contract. Approvals wrap the whole thing wherever a spend needs a second signature.

SECTION 04

The Projects module

This is the centre of gravity. A project is a container: it has a lifecycle, staffing structure, a schedule, a live financial read-out, and six sub-modules of operational detail. Start here, then work outward into §5.

4.1 · Project lifecycle

Status is a free select on the edit form (no forced transitions), but the intended order is:

planning→ active→ on_hold↔ active→ completed→ closed

Types: residential · commercial · industrial · infrastructure · mixed. Two money fields that are not the same thing:

  • Contract value — what the client owes across the job. Drives "outstanding" and the costing profitability view.
  • Budget — the internal spend ceiling. Informational on the detail page.

4.2 · Creating a project

POST /api/projects
  • Sidebar → Projects → New Project.
  • Fill English + Arabic name (both required). Pick a client — address and city auto-populate from that client's record.
  • Pick a Project Manager — the dropdown lists employees with is_manager = true, grouped by department. (Nothing to do with the project_manager login role.)
  • Set contract value, budget, start date, expected completion. Leave code blank — the server assigns PRJ-000N.
  • Save → you land back on the list. Open the card to reach Project Detail.
Verify The Projects list also fans out one GET /api/finance/project/:id per card, so each card shows live outstanding & profit. The portfolio strip up top sums contract value and counts active projects.

4.3 · Anatomy of the Project Detail page

Four bands, top to bottom:

BandWhat's in itSource
Info + finance cardsClient, PM, address, contract value, budget, dates — then Payments collected, Outstanding, Expenses, Profit (green/red)./api/projects/:id + /api/finance/project/:id
Overall completionA single completion_percentage bar for the whole project.project row
PhasesAdd/edit phases, each with its own status & % bar.project_phases
Team & MilestonesTeam members (employees + a role); milestone timeline with target vs achieved dates.project_team, project_milestones

Phases

planning→ active→ completed ·on_hold

Each phase carries a completion_percentage and an optional budget. Work orders can be tagged to a phase.

Team roles

project_manager · site_engineer · qs · safety_officer · supervisor · foreman. Members are picked from HR employees (same source as the staffing PM on the project header) — an employee can only be added once per project (duplicate → 400). Distinct from the project_manager login role used by approvals.

Milestones

Title (EN/AR), a target date, an optional achieved date. Status enum is pending · achieved · delayed; the timeline simply shows a filled node once achieved_date is set.

Test scenario — project skeleton

  • Create a project against CLI-SEED-1. Confirm the code came back as PRJ-000N and address pre-filled.
  • Add two phases ("Foundations", "Superstructure"). Set the first to active at 40%.
  • Add a team member as site_engineer. Re-add the same user → expect the 400.
  • Add a milestone with a past target and no achieved date — it should render as pending on the timeline.
  • Edit the project: bump overall completion to 25%, change status to active. Reload — bars and badges reflect it.

SECTION 05

Project sub-modules — the six tabs

From Project Detail, the quick-link row opens each of these scoped to the current project. They're where the operational cycle actually runs.

A · BOQ — Bill of Quantities

/api/boq  ·  /projects/:id/boq
Model
Sections (nestable via parent_id) contain items. An item has a type (material · labor · equipment · subcontract), a quantity, a unit_rate, and an optional link to an inventory item.
Line total
total_price is a Postgres generated column = quantity × unit_rate. You can't set it directly; it's always consistent.
Progress
completed_quantity on each item is bumped by verified work completions (see tab B).
Summary
GET /api/boq/summary/:projectId groups value & count by type and gives a grand total.
  • GET/api/boq/sections/:projectId — section tree (parents first)
  • POST/api/boq/sections — body needs project_id + name_ar; parent_id optional
  • POST/api/boq/items — body needs project_id + section_id + description_ar
  • GET/api/boq/summary/:projectId — by-type totals + grand total

Cycle to test

  • Add a top-level section "Foundation Works".
  • Add a child section "Excavation" with parent_id = the first section — confirm it nests.
  • Add an item to Foundation Works: Concrete pour, m3, qty 250, rate 1800 → line total should read 450,000.
  • Add an equipment-type item under Excavation.
  • Open the summary — grand total = sum of both lines, split by material vs equipment.

B · Work Orders

/api/work-orders  ·  /projects/:id/work-orders
Status
planned→in_progress→completed·cancelled
Links
Optional phase_id and boq_section_id. The list resolves both to names.
Sub-resources
Materials (issuing with a warehouse_id deducts stock — insufficient stock throws), Labor (planning only, no cost), Equipment (hours × hourly cost → line cost), Completions.
  • GET/api/work-orders/project/:projectId — filter by status / phase_id
  • POST/api/work-orders — needs project_id + title_ar
  • POST/api/work-orders/:id/materials — item_id, actual_quantity, warehouse_id
  • POST/api/work-orders/:id/completions — boq_item_id, quantity_completed, completion_date
  • PUT/api/work-orders/:woId/completions/:compId/verify — {status: "verified" | "rejected"}
The important bit Verifying a completion does three things in one transaction: sets the completion to verified, adds quantity_completed onto boq_items.completed_quantity, and fires work_completion.verified. The cost listener then sums that work order's equipment + labor-payment lines and writes a row into project_costs. This is how field progress becomes cost.

Cycle to test

  • Create a WO titled "Foundation Pour", linked to the BOQ Foundation section.
  • Move it to in_progress.
  • Add an equipment line: 40 hrs × 15,000 → cost 600,000.
  • Record a completion against the concrete BOQ item, quantity_completed = 100.
  • Verify it. Re-open the BOQ item → completed_quantity is now 100. Check /api/costing/project/:id → a new project_costs row for the equipment total.

C · Site Management

/api/projects/:projectId/(site-reports · site-visits · instructions)  ·  /projects/:id/site
Daily reports
One per project per date (unique constraint → 409 on a duplicate). Weather, temperature, worker count, work summary (required), materials received & equipment on site (free text — not linked to inventory).
Site visits
Visitor name/role, notes, and an action_items array of {text, done}.
Engineer instructions
Auto-numbered EI-<projectId>-NNN, a priority, and a strict state machine.
issued→ acknowledged→ implemented→ closed

Transitions are enforced server-side — you can't skip a step, and a closed instruction is read-only.

Cycle to test

  • File a daily report for today. File a second for the same date → expect the 409.
  • Log a site visit with two action items, one marked done.
  • Issue an instruction at high priority. Try to jump it straight to implemented → rejected. Walk it acknowledge → implement → close. Try to edit it after closing → 400.

D · QHSE — Quality, Health, Safety, Environment

/api/qhse  ·  /projects/:id/qhse
Quality tests
A test_type, a result of pass / fail / pending, optional link to a BOQ item.
NCRs
Non-conformance reports. Auto NCR-YYYY-####, severity minor · major · critical, optional link to a quality test.
Inspections
A checklist_items JSONB array of {item, ok, note}, findings, status pending · passed · failed.
Incidents
Severity, injured party, corrective action; status open · investigating · closed.

NCR state machine (a resolved NCR can be re-opened; a closed one is read-only):

open→ in_progress→ resolved→ closed ↺ resolved → in_progress

Cycle to test

  • Log a quality test with result fail against a BOQ item.
  • Raise an NCR (major) linked to that test. Note the NCR-2026-#### number.
  • Advance it open → in_progress → resolved with resolution notes, then re-open to in_progress, then resolved → closed.
  • Log a safety inspection with a 3-item checklist and a failed status. Report an incident and close it.

E · Project Documents — Document Control

/api/docs  ·  /projects/:id/documents
Categories
Nestable folders (parent_id).
Documents
A document_type (drawing · contract · report · photo · rfi · other) and a file_url. Files are uploaded first via /api/documents/upload (multer → local backend/uploads/), then the URL is stored here.
Versioning
Creating a doc records v1. POST /:id/versions bumps the version, archives the prior file in document_versions, and resets status to draft with approval cleared — a new revision needs re-approval.
Approval
POST /:id/approve or /reject stamps approver + timestamp.
RFIs
Auto RFI-<projectId>-NNN. open → respond → answered → close → closed. An open RFI past its due date shows is_overdue.
Submittals
material · shop_drawing · sample · method; respond with under_review · approved · rejected · revised.
Not the same as Legal This module (project_documents) is entirely separate from the sidebar Legal module (legal_documents) — different tables, no FK, no overlap. Legal is org-wide; this is per-project.

Cycle to test

  • Create a category "Structural Drawings".
  • Upload a document into it (type drawing). Approve it.
  • Upload a v2 via the versions endpoint — confirm version is 2, status snapped back to draft, and document_versions holds both.
  • Raise an RFI with a past due date → is_overdue true. Respond, then close.
  • Create a shop_drawing submittal and respond approved.

F · Units & Sales

/api/sales  ·  /projects/:id/units
Buildings
Code unique per project, floors, units-per-floor, status planning · under_construction · completed.
Units
Type (apartment · villa · penthouse · studio · townhouse · duplex · commercial · plot · office), finishing type, area, price. price_per_m2 is derived.
Bulk generator
POST /buildings/:id/bulk-units spins up floors × units_per_floor units from a prefix (e.g. prefix "A", floor 1 → A101, A102…). Code collisions → 409.
Summary
GET /api/sales/summary?project_id= — counts & price totals by status, plus a per-client breakdown of contracted / invoiced / paid.

Unit sales flow (block is a side state; going back to available clears client & sold amount):

available→ reserved→ contracted→ delivered→ closed ·blocked ↔ available
Auto-invoice Moving a unit to contracted with a client attached auto-creates an invoice (INV-000N, status sent) for sold_amount (or list price). client_id is required for reserved and contracted. Guards: can't delete a building with sold units; can't delete a reserved/sold unit.

Cycle to test

  • Create a building "Block A", 5 floors × 4 units.
  • Bulk-generate the 20 units at 1,200,000 each.
  • Reserve one unit — try without a client_id first (→ 400), then with CLI-SEED-2.
  • Contract that unit with a sold_amount. Check Invoices → a new INV-000N for that amount, tied to the project & client.
  • Open the sales summary — the client breakdown shows the contracted amount and the auto-invoice.
  • Try to delete the building → blocked.

SECTION 06

Project finance & job costing

Two endpoints report a project's money, and they answer different questions — don't expect them to match.

 /api/finance/project/:id/api/costing/project/:id
Question"How's cash on this job?""Is this job profitable against contract?"
Revenue sidetotal_invoiced = Σ invoices · total_paid = Σ paymentsrevenue = project contract_value
Cost sidetotal_expenses = Σ expensesΣ project_costs (from cost events)
Outstandingtotal_invoiced − total_paid—
Profittotal_paid − total_expensescontract_value − Σ project_costs, plus a margin %

Where project_costs rows come from

An in-process event bus (costEventListener.js) listens for three events and writes cost rows tagged with a cost code:

  • work_completion.verified → sums that WO's equipment + labor payments → cost code 11 (labor).
  • labor_payment.created → the payment total → cost code 11.
  • sub_payment.paid → a subcontractor payment certificate → cost code 12 (subcontract).

The Project Detail finance cards use the finance endpoint. The /api/costing/project/:id/summary endpoint joins cost codes against project_budgets to give a budget-vs-actual line per code.

SECTION 07

Company money: expenses, invoices, payments

Expenses

/api/expenses  ·  sidebar: Expenses
Model
Category, amount, date, an optional project_id (project-less overhead is allowed).
Status
pending → approved / rejected, driven by the approvals workflow (module expenses, stage-1 role finance_manager).
Feeds
The project finance endpoint's total_expenses and the global finance summary.

Invoices

/api/invoices  ·  sidebar: Invoices
Create
Needs project_id + client_id + positive amount + issue_date. Number auto-assigned INV-000N; opens at status sent.
Status
draft · sent · partially_paid · paid · overdue — recomputed lazily on every GET from Σ payments vs amount and the due date. It is not written on payment create/delete, so a stale status can exist between a payment change and the next read.
Delete
Blocked with a 400 if any payment is linked. Remove payments first.
draft→ sent→ partially_paid→ paid ·overdue

Payments

/api/payments  ·  (recorded from an invoice)
Model
Linked to an invoice_id (also carries project_id + client_id). Method, reference number, date.
Effect
The parent invoice's status is recalculated on its next GET. Deleting a payment reverses it the same way.

Cycle to test

  • Create an invoice for 50,000 against your test project + client.
  • Record a payment of 30,000. Re-GET the invoice → partially_paid.
  • Record 20,000 more → paid, outstanding 0.
  • Try to delete the invoice → 400. Delete both payments, then the invoice → succeeds.

The global Finance summary (/api/finance/summary) aggregates all payments, invoices and expenses into revenue collected, total invoiced, outstanding, net profit and an overdue count. The Dashboard surfaces the same headline figures.

SECTION 08

Approvals — the cross-cutting workflow

Any module that needs a second signature raises an approval request. It's a two-stage chain.

submitted→ manager_review→ owner_review→ approved ·rejected (either stage)

A few modules (purchase_orders, grn) skip straight to owner_review. Everything else starts at manager_review, gated by a module→role map:

ModuleStage-1 (manager) roleOn full approval, source becomes…
expensesfinance_managerapproved
payrollfinance_managerapproved
legallegal_mgrverified
assets / maintenancemaintenance_mgr(no status change wired)
project_budgetsproject_managerapproved
sub_contractsproject_manageractive (reject → terminated)

Rules that bite

  • You cannot approve or reject your own request — unless you're owner/admin.
  • A manager-stage approver must hold the mapped role for that module. Owner/admin can act at any stage.
  • Owner/admin see all pending requests; a manager sees only manager_review rows for their modules.
  • A reject at either stage flips the source record straight to rejected/terminated.

Endpoints

  • POST/api/approvals/request — {module_name, request_type, request_id, notes}
  • GET/api/approvals/pending — scoped to your role
  • PUT/api/approvals/:id/approve — advances one stage, or finalises
  • PUT/api/approvals/:id/reject
  • GET/api/approvals/my-requests — things you raised
  • GET/api/approvals/audit — owner/admin, non-pending history
  • GET/api/approvals/:id/details — request + underlying record + Submitted→Manager→Owner timeline

Cycle to test — an expense through both gates

  • As test-staff@test.com, create an expense for 8,000 on your project.
  • POST /api/approvals/request with module_name: "expenses", request_id = that expense id.
  • As test-finance-mgr@test.com, open Approvals → Pending. The row is clickable → the detail modal shows the expense fields + timeline. Approve → stage moves to owner_review.
  • As owner, approve again. The expense status is now approved and it appears in the Audit tab.
  • Repeat but have the finance manager reject at stage 1 → expense goes rejected immediately.

SECTION 09

The golden-path test script

One continuous scenario that touches every module in cycle order. Do it as owner for the first pass (no permission friction), then repeat the approval leg with the two test roles. Expect ~20 minutes.

  1. Client — create "Marina Bay Holding" (or reuse CLI-SEED-1).
  2. Project — new project against that client, contract value 8,000,000, budget 6,000,000. Note the PRJ-000N code.
  3. Structure — add phases "Substructure" & "Superstructure"; add yourself to the team as project_manager; add a milestone "Ground floor slab" dated next month.
  4. BOQ — section "Concrete Works" → item C30 pour, m3, qty 400, rate 2,000 (line = 800,000); nested section "Rebar" → item Rebar fix, ton, qty 60, rate 38,000.
  5. Work order — "Slab pour WO-1" against Concrete Works; move to in_progress; add an equipment line 24 hrs × 15,000.
  6. Site report — file today's daily report: 30 workers, weather sunny, summary "First slab section poured".
  7. QHSE — quality test "Slump test" = pass; raise a minor NCR on a honeycomb patch and walk it to closed.
  8. Documents — upload "Slab shop drawing" (type drawing), approve, then push a v2 and watch it drop to draft. Raise + answer + close one RFI.
  9. Completion — record a completion on the C30 pour BOQ item, qty 150; verify it. Confirm: BOQ completed_quantity = 150, and /api/costing/project/:id gained a cost row for the WO equipment.
  10. Invoice — raise INV-000N for 2,000,000 against the project + client.
  11. Payments — record 1,200,000 then 800,000. Re-open the invoice between each → partially_paid then paid.
  12. Expense + approval — log a 45,000 "Concrete supply" expense on the project; raise the approval request; approve through finance_manager then owner.
  13. Finance read-out — open Project Detail. Cards should show payments collected 2,000,000 · outstanding 0 · expenses 45,000 · profit 1,955,000 (paid − expenses).
  14. Sales branch — add building "Tower 1" (10 × 6); bulk-generate 60 units at 1,500,000; reserve one to CLI-SEED-2; contract it for 1,450,000; confirm a fresh INV-000N appeared automatically.
  15. Roll-up — check the Dashboard, the global Finance summary, and the Approvals → Audit tab all reflect the run.

SECTION 10

Gotchas & known quirks

Things that look like bugs but aren't (or are, and you should know):

Stale dev-process class If a route or i18n key looks correct in source but the bug still reproduces live, suspect a long-running node server.js / npm start that started before the fix. Check the port's PID creation time against the file mtime; kill & restart before debugging further. This has burned people more than once.
Migrations are manual The local DB drifts from route code. Migration scripts are standalone and idempotent but must be run by hand — a route referencing a table that "doesn't exist" usually means an un-run migrate-*.js.
  • Two different "Project Managers". The project header PM is an employee (is_manager = true, FK to employees, display only). The project_manager approval role is a login user role. They're unrelated.
  • NCR status has no role gate. Any authenticated user can advance any NCR through its transitions. There's no assignee field — only raised_by / resolved_by.
  • Invoice status is lazy. It's recomputed on GET, not written on payment mutation — a stale value can exist for one read.
  • Bilingual creates. name_ar / title_ar / description_ar is required on most POSTs; the English and plain name columns are back-filled from it if omitted.
  • Delete behaviour is mostly hard delete. Guarded only on invoices (linked payments), buildings/units (sold), and a few FK checks. Clients & suppliers soft-delete via is_active.
  • Site "materials received" / "equipment on site" are free text — not linked to Inventory or Assets, unlike BOQ's item picker.
  • Units historically had no client link. Now client_id is captured on the status transition and is required for reserved/contracted; there's still no payment-plan model.
  • project_documents ≠ legal_documents. Separate tables, no relationship.
  • CI builds. CI=true production builds fail on pre-existing ESLint unused-var warnings in some Part-1 pages — not your change.

Cross-checked against SYSTEM_TEST_REPORT.md (158/158 assertions, 18 modules) — use that report for the exact per-assertion expectations.
