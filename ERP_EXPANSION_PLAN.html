What the spec changes, phase by phase

The 112-section specification is not a different product. It is written to sit on top of what is already built — same stack, same database, same API style — and expand it roughly fourfold. This is the map of that expansion: what gets added, modified, and removed at each of the 27 phases.

Verdict: adapt and expand, do not rebuild. Around 90 % of the work is additive (new tables and routes beside the current schema) or refactor (hardcoded logic → configurable engine). Genuine deletions are a handful of shortcut constants and three tables that fold into a unified model. Three phases are structural and must land first because they touch live foreign keys: Organizations, Permissions, and Locations + BOQ allocation.

Where the product stands today

Audited from the running codebase — migrations, route files, and React pages.

Stack
Express + PostgreSQL + React. Relational, project-scoped. Exactly the architecture the spec assumes.
Execution
Solid. work_orders with materials / labour / equipment / completions, and sub_work_verifications. This is the spine the spec builds on and explicitly credits.
BOQ
boq_sections + boq_items with a single completed_quantity. No location dimension, no cost dimension, no certified-vs-executed split.
Structure
buildings (floors stored as an integer, not rows) and units (for sales). No site / zone / floor / area / room tree.
Permissions
Flat users.role string + module_permissions[]. authorize() is a role-list check with an owner/admin bypass. No org, project, record, or financial-visibility scoping.
Approvals
One generic 2-stage flow (manager_review → approver) with a hardcoded MODULE_MANAGER_ROLES map. A proto-workflow engine, not configurable.
Parties
Three separate tables — clients, suppliers, subcontractors. No unified Organization. No consultants.
Procurement
Absent. No PR / RFQ / quotation / PO / GRN. Spend is captured as expenses + invoices + payments.
Inventory
warehouses + warehouse_stock + inventory_transfers. No movement ledger, no GRN/MIR gate, no reservations, no reorder logic.
Commercial
sub_contracts, sub_payment_certificates, project_budgets, cost_codes, journal entries. Profit is contract_value − total_cost — no forecast model, no client-side certificates, no variations.
RFI / Submittal
project_rfis / project_submittals — single-answer, not multi-stage.
QHSE
ncrs, quality_tests, safety_incidents, safety_inspections, site_visits, site_daily_reports. Basic; no ITP / WIR / MIR / permits.
Doc control
document_categories + document_versions — already has revision history and approval reset. Good base to make enterprise-grade.
Property sales
units + buildings carry reservations/contracts for unit sales. Not in the spec's core construction model — §81 says keep it as an optional Property Development module, not fold it into the main workflow.
HR / Payroll / Legal / Assets
Four modules — hr.js, payroll.js, legal.js, maintenance.js — plus an employees table, built after this audit's original baseline. None of it maps to a numbered spec section except the org chart (§4: HR, Legal, Plant & Equipment as departments) and §52 Resource/Labour (timesheets, cost rate feeding labour cost). Not org-scoped, not permission-engine-aware, no workflow hooks — needs its own gap pass before Phase 3 locks the permission model.
In-flight drift
An uncommitted migration already re-points project_team.user_id (login account) to project_team.employee_id (staffing record). Phase 3's absorption of project_team into project_participants must design against this employee-based shape, not the pre-migration one.
Absent entirely
Client / consultant / subcontractor / supplier portals · action & notification engine · scheduling · reporting engine · versioned API · MCP · immutable audit log (only a mutable activity_log) · handover / warranty / DLP · site-operations daily workspace · backup, observability & DR posture.

Migration risks — the parts that touch live data

High-risk — sequence carefully, migrate with rollback

  • Phase 3 (Organizations). Re-points projects.client_id and every party FK. Do it behind compatibility views so no route breaks mid-migration; cut callers over one module at a time.
  • Phase 4 (Permissions). Every route currently trusts authorize(). Keep that function as a facade over the new policy engine so the 28 route files don't all change at once; migrate users.role to role assignments with the old columns retained as fallback until parity tests pass.
  • Phase 8 (Locations + BOQ allocation). boq_items.completed_quantity becomes derived and work_completions gains required location/allocation FKs. Backfill existing completions to a default location before enforcing NOT NULL.
  • Phase 6 (Workflow engine) and Phase 13 (commercial model). Migrate approval_requests rows and recompute historical profit under the new forecast model; keep the old figures snapshotted for audit.
  • Phase 3 again — project_team. A migration already in progress re-points it from users to employees; sequence the participants refactor so it lands on top of that, not against the pre-migration shape.

Everything else — procurement, notifications, scheduling, site operations, portals, reporting, handover, API, MCP, security hardening — is new tables and new routes alongside the current schema, with no destructive change to existing data.
